# RedisLite — дизайн проекта

Дата: 2026-10-08
Срок реализации: 2 месяца (8 недель)

## 1. Цель проекта

Сетевой in-memory key-value сервер на C++ (аналог Redis Lite) с поддержкой
базовых команд (`GET`, `SET`, `DEL`), TTL для ключей и транзакций
(`BEGIN`/`COMMIT`/`ROLLBACK`). Клиенты подключаются по TCP (сокеты) и
обмениваются командами в простом текстовом протоколе.

## 2. Общая архитектура

```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│  Client 1   │      │  Client 2   │      │  Client N   │
│ (telnet/nc) │      │             │      │             │
└──────┬──────┘      └──────┬──────┘      └──────┬──────┘
       │ TCP                │ TCP                │ TCP
       ▼                    ▼                    ▼
┌─────────────────────────────────────────────────────────┐
│                      Server (accept loop)                │
│        на каждое новое подключение — новый std::thread    │
└──────┬──────────────────┬──────────────────┬─────────────┘
       │ thread 1          │ thread 2          │ thread N
       ▼                   ▼                   ▼
┌─────────────────────────────────────────────────────────┐
│            Command Parser + Session state                │
│   (у каждого потока своё: буфер чтения, флаг "в транзакции│
│    ли клиент", очередь отложенных команд)                  │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│              Storage (единый объект на сервер)            │
│   std::unordered_map<string,string> + TTL map              │
│   защищён одним std::mutex (+ std::recursive_mutex          │
│   для удержания лока на время всей транзакции)              │
└──────────────────────────┬──────────────────────────────┘
                           ▼
                 ┌───────────────────┐
                 │  Persistence       │
                 │  (snapshot в файл) │
                 └───────────────────┘
```

Главная идея: один процесс, один общий `Storage`, доступ к нему всегда
идёт через mutex — это даёт простую и предсказуемую семантику транзакций
(глобальная блокировка = ACID за счёт сознательного отказа от
параллелизма внутри транзакции).

Модель конкурентности: **thread-per-connection** — на каждое клиентское
соединение сервер создаёт отдельный `std::thread`.

Платформа: **Linux/macOS, POSIX sockets** (без поддержки Windows/Winsock).

## 3. Компоненты

| Компонент | Ответственность | Зависит от |
|---|---|---|
| `TcpServer` | `socket()`/`bind()`/`listen()`/`accept()`, на каждое подключение спавнит `ClientSession` в новом потоке | — |
| `ClientSession` | Читает байты из сокета, собирает строки по `\n`, вызывает `CommandParser`, пишет ответ обратно в сокет. Хранит своё состояние: `in_transaction`, очередь команд транзакции | `CommandParser`, `CommandExecutor` |
| `CommandParser` | Разбирает строку вида `SET key value` в структуру `Command{name, args[]}`. Валидирует число аргументов | — |
| `CommandExecutor` | По `Command` вызывает нужный метод `Storage` (GET/SET/DEL) или управляет транзакцией (BEGIN/COMMIT/ROLLBACK), формирует текстовый ответ | `Storage` |
| `Storage` | Потокобезопасное key-value хранилище: `unordered_map<string,string>` + `unordered_map<string, time_point>` для TTL. Методы `get/set/del/exists`, `lock()/unlock()` для транзакций | `std::mutex` |
| `TtlReaper` | Фоновый поток, раз в N миллисекунд проходит по TTL-карте и удаляет просроченные ключи | `Storage` |
| `PersistenceManager` | `saveSnapshot(path)` — сериализует всю карту в файл; `loadSnapshot(path)` — вызывается при старте сервера | `Storage` |
| `main.cpp` | Читает конфиг (порт, путь к snapshot-файлу), поднимает `Storage`, грузит snapshot, запускает `TtlReaper`, запускает `TcpServer` | всё вышеперечисленное |

Каждый компонент — отдельные `.h`/`.cpp`, тестируемые изолированно
(`Storage` и `CommandParser` не знают о сети — юнит-тестируются без
сокетов).

## 4. Протокол команд

Формат запроса: одна строка, разделитель `\n` (принимаем и `\r\n`,
обрезая `\r` на конце).

```
<COMMAND> [arg1] [arg2] ...
```

| Команда | Пример | Ответ (успех) | Ответ (ошибка/edge case) |
|---|---|---|---|
| `SET key value` | `SET name Alex` | `OK` | `ERROR wrong number of arguments` |
| `GET key` | `GET name` | `Alex` / `(nil)` если нет ключа | — |
| `DEL key` | `DEL name` | `OK` (даже если ключа не было) | — |
| `EXPIRE key seconds` | `EXPIRE name 10` | `OK` | `ERROR no such key`, `ERROR invalid expire time` |
| `TTL key` | `TTL name` | секунды, `-1` без TTL, `-2` если ключа нет | — |
| `SAVE` | `SAVE` | `OK` | — |
| `BEGIN` | `BEGIN` | `OK` | `ERROR transaction already started` |
| `COMMIT` | `COMMIT` | см. раздел 5 | `ERROR no transaction` |
| `ROLLBACK` | `ROLLBACK` | `OK` | `ERROR no transaction` |
| `PING` | `PING` | `PONG` | — |

Значения — однословные строки без пробелов (упрощение; поддержка
значений с пробелами через кавычки — опциональная фича при наличии
времени).

Вложенные `BEGIN` не поддерживаются (ошибка).

## 5. Семантика транзакций

- `BEGIN` переводит сессию в режим накопления: **все** последующие команды
  (включая `GET`/`TTL`) не исполняются сразу, а складываются в очередь
  команд этой сессии, отвечая `QUEUED`. Это соответствует настоящему
  Redis `MULTI`/`EXEC` и гарантирует, что клиент не увидит промежуточное
  состояние транзакции.
- `COMMIT`: сервер захватывает глобальный mutex на всё время выполнения
  очереди, последовательно применяет все накопленные команды к
  `Storage`, освобождает мьютекс. Ответ:
  ```
  COMMIT_OK <N>
  <результат команды 1>
  <результат команды 2>
  ...
  <результат команды N>
  ```
  где `<N>` — число выполненных команд, далее по одной строке результата
  на каждую команду, в порядке очереди (в том же формате, что и у
  соответствующей команды вне транзакции). Если при выполнении одной из
  команд возникает ошибка, на её позиции будет `ERROR ...`, остальные
  команды всё равно выполняются.
- `ROLLBACK`: очищает очередь команд сессии без применения, отвечает `OK`.
- Обрыв TCP-соединения без `COMMIT`/`ROLLBACK` трактуется как неявный
  `ROLLBACK`.

## 6. Персистентность (snapshot)

Формат файла — текстовый, один ключ на строку:
```
<key> <value> <expire_unix_timestamp_or_-1>
```

- Сохранение: по команде `SAVE`, автоматически каждые N секунд фоновым
  потоком (конфигурируемый интервал), и при штатном завершении сервера
  (`SIGINT`/`SIGTERM`).
- Загрузка: один раз при старте `main()`, до открытия порта для клиентов.
  Если файла нет — старт с пустым хранилищем.
- Консистентность: снимок данных копируется из `Storage` под тем же
  глобальным mutex (быстрая операция), запись в файл происходит уже без
  удержания лока, чтобы не блокировать клиентов на время дисковой записи.

## 7. Обработка ошибок и edge cases

- Некорректная команда (неизвестное имя, неверное число аргументов):
  `ERROR <описание>`, соединение не рвётся.
- Обрыв соединения клиента: `recv() == 0` → закрыть сокет, отбросить
  незакоммиченную транзакцию, завершить поток сессии.
- Ключ не найден — штатный ответ, не ошибка (`(nil)`, `OK` для `DEL`,
  `-2` для `TTL`, `ERROR no such key` для `EXPIRE`).
- Некорректный формат числа в `EXPIRE`: `ERROR invalid expire time`.
- Слишком длинная строка команды (> 64 КБ) без разделителя: обрыв
  соединения с `ERROR line too long`.
- Исключение внутри обработки команды оборачивается в `try/catch` на
  уровне `ClientSession`: ответ `ERROR internal error`, сервер не падает.
- `SIGINT`/`SIGTERM`: graceful shutdown — сохранить snapshot, закрыть
  listening socket, дать текущим клиентам завершиться (или форсированно
  закрыть по таймауту), выйти.

## 8. Тестирование

- **Юнит-тесты** (GoogleTest, подключение через CMake `FetchContent`):
  - `Storage`: `set/get/del`, истечение TTL, конкурентный доступ из
    нескольких потоков.
  - `CommandParser`: корректный разбор всех команд, обработка
    некорректного ввода.
  - `PersistenceManager`: save → load → данные совпадают.
- **Интеграционные тесты**: реальный `TcpServer` на тестовом порту в
  фоновом потоке, подключение обычным TCP-клиентом; сценарии
  `SET`→`GET`, `BEGIN`/.../`COMMIT`, `ROLLBACK`, несколько клиентов
  одновременно.
- **Ручное тестирование**: `telnet`/`nc` во время разработки.
- **Нагрузочная проверка** (опционально): N параллельных соединений,
  проверка на падения и утечки памяти/дескрипторов.

## 10. Помесячный план (8 недель)

| Неделя | Цель | Результат |
|---|---|---|
| 1 | Знакомство с POSIX sockets: `socket/bind/listen/accept/recv/send`. Мини-эхо-сервер | Работающий TCP echo-server, `telnet` видит эхо |
| 2 | `TcpServer` + `ClientSession` на thread-per-connection. Базовый `CommandParser` (`SET`/`GET`/`DEL`/`PING`) без реального хранилища | Несколько клиентов одновременно шлют команды, получают ответы |
| 3 | `Storage` с `std::mutex`, интеграция `CommandExecutor` | Полный рабочий цикл SET/GET/DEL, потокобезопасно, первые юнит-тесты (GoogleTest подключён) |
| 4 | `EXPIRE`/`TTL`, фоновый `TtlReaper`. Обработка ошибок и edge cases (раздел 7) | Ключи с TTL истекают сами, сервер не падает на мусорном вводе |
| 5 | Транзакции: состояние сессии, очередь команд, `BEGIN`/`QUEUED`/`COMMIT`/`ROLLBACK`, формат `COMMIT_OK <N>` | Транзакции работают сквозной сценарий, есть интеграционные тесты на них |
| 6 | `PersistenceManager`: `SAVE`, автосохранение по таймеру, загрузка при старте, graceful shutdown по `SIGINT`/`SIGTERM` | Данные переживают перезапуск сервера |
| 7 | Расширение юнит- и интеграционных тестов, прогон конкурентных сценариев, фикс найденных багов | Зелёный прогон всех тестов |
| 8 | Нагрузочная проверка, полировка кода, README с инструкцией сборки/запуска/примерами команд, буфер на непредвиденное | Готовый к сдаче/демонстрации проект |

Неделя 8 — буфер: учитывая отсутствие опыта с сокетами/потоками, недели
1–3 могут занять больше времени, чем ожидается; буфер компенсирует это
без сдвига общего срока.
